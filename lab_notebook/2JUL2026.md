# 2 June 2026

A few extra fixes needed to happen for phase_common. In collaboration with Claude, I outline the work that needed to happen before the fix was found. I'll then describe what I learned, and how that can inform the next development cycle.

This morning, I implemented the AC/AN tag fixes using <code>bcftools +fill-tags</code>. I learned about how the AC and AN tags worked from the VCF specification document but also a StackOverflow post.

Some runs then succeeded, but I noticed that some phase_common jobs were failing, while some others were not (I was succeeding on phase_common for chr17 but not chr15, for some reason, even after forcing reruns).

Using <code>sacct -j</code> I identified that some jobs were failing because they were CANCELLED+ and some failed with a non-zero exit code. The former is distinguished by 0:9 exit code in SLURM, the latter by 0:1.

Using <code>sacct</code> with output options for requested and used memory resolved that a lack of memory was not the only issue, although the CANCELLED+ tags were definitely because of memory overflow. Because the jobs that FAILED were so fast and didn't request that much memory, however, _that resolved the memory hypothesis_.

Claude presented some alternate hypotheses after the memory fixes were implemented. One was that the _T2T builds between HPRCv1 and HPRCv2 were different_. This was unlikely, and using: <code> bcftools view -h results/split_target/combined_chr15.bcf | grep contig </code> on the HPRCv1 and HPRCv2 panels showed that they were largely the same. The sample VCFs themselves don't have contig information in their headers, although I could assume they look like the panel they genotyped from, HPRCv1. For what it's worth, some research shows that HPRCv2 uses T2Tv2 and HPRCv1 uses T2Tv1. See the following links, based off the PanGenie wiki:

<https://s3-us-west-2.amazonaws.com/human-pangenomics/pangenomes/scratch/2026_03_30_pangenie/README.txt>
<https://zenodo.org/records/7839719>

Claude noticed that some of the VCFs mentioned 44 samples in the reference panels, others mentioning 231. I did a force rerun in Snakemake and used bcftools query and got the all clear.

I decided to just run it directly and got things printed to stderr that I didn't notice at all! The error message:

<code>phase_common: src/utils/xcf.h:619: int32_t xcf_reader::readRecord(uint32_t, char**, char**, int32_t*): Assertion `max_ploidy==ploidy[file]' failed.</code>

Claude recognized this as a ploidy issue and suggested using this command to check for haploid sites:
<code>bcftools view -H panel_chr15.bcf | awk '{for(i=10;i<=NF;i++) if($i !~ /[\/|]/) {print; break}}' | head</code>

I used the command and noticed all of the records had a missing genotype <code>.</code> that was haploid. Claude noticed that these records piled up very densely at similar coordinates, despite having slightly different offset coordinates. This was my first view of a complex locus! Claude suggested using <code>bcftools +fix-ploidy</code> or <code>bcftools norm </code>. The first one simply converts haploids into diploids, and the second one merges a bunch of stacked biallelic records--records at the same location--into one multiallelic record and then pruning out the multiallelics.

I didn't want to lose variants by pruning, although I figure that not that many polymorphic TEs can be complex loci. I also worried that multiallelic norming is hard. I used a local run <code>bcftools plugin fixploidy combined_chr17.bcf | bcftools filter -i 'GT="mis"' | bcftools view | less</code> to confirm that the ploidy fixes worked. This seems to have fixed phase_common.

I had to add some additional fixes to concat_chrs. Most were small typos, but one big error was that the echo line <code>echo "{input.bcf}" | sed 's/ /\n/g' | sort -t "_" -k3,3n > tmp/input_bcf.txt"<code> didn't really work, since I think that newline character (which should convert the input line into a top-down list) actually ends up escaping as a Python string character! I just ran most of the commands manually, which wasn't an issue.

Things learned:

* VCF structure (AC/AN tags, multiallelics, complex loci)
* how memory overflows are reported in SLURM
* silent errors in stderr not getting piped (both from echo, bcftools, and SHAPEIT)

Coding design patterns:

* How to use <code> bcftools view, bcftools isec, bcftools query, bcftools stats</code>. Largely, bcftools likes to pipe through stdout, and I learned that bcfs are so fast and easy to handle with <code>less</code>.
* Generally speaking, testing is much faster than reading documentation OR spinning up Snakemake! This is why modular development of scripts is important. I should also learn how to set up argument flags to make it easier to stick a script into the body of a Snakemake directive.
* Silent errors are very common. Again, that's why I need to be testing locally, as not everything is caught by stderr redirects or log flags.
* indexing files, making them easily read, working on chunks--these are all incredibly important for quickly testing code! Make sure you know how a given file format/parsing library wants to read its data.
