## bedtools intersect

I bring up the bedtools intersect because I know the method is wrong but that intersecting Xiaoyu's .bed file with PanGenie genotypes yields **2400 potential TEs**, which Juan thinks is quite good!

We talk about whether the bedtools strategy works.

* I start by taking the insertion points and slopping them downstream by their consensus length to get a feature the length of the TE at the appropriate start site.
* Juan points out that this includes overlaps with bad features for two reasons
   * using the -r or reciprocal percentage bedtools flag means large elements have way more leeway in ABSOLUTE bases (e.g. LINE vs Alu)
   * slopping by the length keeps records that shift downstream. If your element is too far upstream, you lose reciprocal percentage. But if your element shifts downstream and is similar in length, it can actually remain fully inside the Xiaoyu .bed feature!

The best solution would be to use a tool like Truvari, which is designed for structural variant harmonization between two VCFs. To create a VCF for Truvari, however, I would also need the allele per consensus feature in the bed file. Since every individual has their own slightly different allele, how would I merge them? Juan suggests that one answer is to get the consensus allele directly from RepeatMasker (if this feature is by consensus L1PA2, you could just get the known sequence of L1PA2 in the RepeatMasker sequence library and use Truvari to compare that to your own VCF).

Of course, this would be quite a bit of work. Besides, Truvari isn't perfect. A simpler way would be to test the insert position, symmetrically slopped by a constant number of bp (20 maybe?) and checking for length and variant type too. Even checking the length isn't too necessary, as the chances of indels occuring that closely is low. But in my opinion I should do it anyways. ## phasing

Juan still thinks there are issues with vg's calling. I also my Pangenie/Xiaoyu intersect is pretty good, but I go down to 287 phaseable TEs when intersecting with SHAPEIT5.

Juan points out the issue of switch errors--that haplotype blocks are pretty neat up to a certain length, but not chromosome spanning. There comes a point where a bunch of recombination happens at a certain locus, and there is no clear linkage between the previous and next haplotype block. The statistical power offered by linkage drops off, basically.

The result is that it is very hard to phase across an entire chromsome, which SHAPEIT attempts to do. If it cannot cleanly phase a variant to mat/pat it will simply drop it, leaving entire haplotype blocks out of the phased results. Even if the individual haplotype blocks are phasable within themselves, they can't be phased _consistently between each other, and blocks are dropped out_.

Juan points out that we want to phase for ASE to look for _cis-genetic effects_, so we don't need to phase across the entire chromosome. We only need to phase within cis-regulatory distance, i.e. within a TAD. Juan proposes finding consensus TAD boundaries across a panel and using that to chunk chromosomes and perform SHAPEIT per TAD to do ASE within a TAD. Although TADs are conserved across individuals, we would have to guess if TADs are applicable across cell types. Maybe you can build tooling for this?

The point ultimately is that _these are not terrible numbers_. There is a double constraint on phasable TEs. They need to be young enough that they are polymorphic, but old enough that they reliably appear in haplotype blocks and are thus phasable, and then anyways they have to survive these differences between haplotype blocks (switch errors).
